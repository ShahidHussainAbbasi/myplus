Till Row Layout

Design review · POS line entry · id="Sell"

Two ways to make the till a table

Both put the labels in one band and the inputs in another. They differ in how they survive the thing that happens on every real installation: a shop switching half the fields off. Toggle the switches below and watch which one stays a table.

Today

Caption per field, held in place by negative margins

.pos-rowentry makes #Sell a flex row and glues each caption to its own field. The CSS says why that is awkward, in its own comment: “Flex has no ‘keep these two adjacent’ primitive, so each label is pulled flush against its field.”

The captions are not a row. Each one is a separate flex item sitting beside its field, so the band only looks like a header while every label happens to be one line and similar in width. “Receiveable” and “S/U Price” next to “Qty” already pull it out of true, and a wrapped label breaks it.

It is also why hiding a field is delicate — two elements have to disappear together, coordinated by a data-pos-field attribute repeated on both.

Option A

CSS Grid over the markup you already have

Same DOM. #Sell becomes a grid; captions are pinned to row 1, fields to row 2, and the grid flows in columns. No template surgery — about thirty lines of CSS and three missing labels.

.pos-rowentry #Sell{
  display:grid;
  grid-auto-flow:column;          /* label then field fills a column, then move right */
  grid-template-rows:auto auto;   /* row 1 = captions, row 2 = inputs                 */
  gap:5px 10px;
  align-items:end;
}
.pos-rowentry #Sell .control-label{ grid-row:1; }
.pos-rowentry #Sell [class*="col-sm-"]{ grid-row:2; }

/* the full-width blocks living inside #Sell must opt out of the column flow */
.pos-rowentry #Sell .pos-fullrow,
.pos-rowentry #Sell .text-center{ grid-column:1 / -1; }

Three fields have no label at all — bexpDate, sellDiscountTypeDD and sellsrp. Under a header row they would sit beneath blank cells, so they need labels either way. They should have had them regardless: an unlabelled input is its own usability bug.

The awkward part is that the scan row, the batch-info alerts and the button row all live inside #Sell and interrupt a column-flow grid. grid-column:1/-1 handles it, but the ordering has to be right and it is easy to disturb later.

Option B

One cell per field, caption inside it

Each label and its input are wrapped in a single cell. The row becomes a strip of identical cells, so the captions line up because of the structure rather than because the CSS is asked to hold them there.

.pos-rowentry #Sell{ display:flex; flex-wrap:wrap; align-items:flex-end; gap:10px; }
.pos-rowentry .pos-cell{ display:flex; flex-direction:column; gap:5px; }
.pos-rowentry .pos-cell .control-label{ height:13px; }   /* one common caption band */

One attribute instead of two. data-pos-field moves onto the cell, so hiding a field removes the caption and the input together — they cannot come apart, because they are one element. Today the same attribute is repeated on the label and the column, and the pair stays together only as long as nobody edits one of them.

The negative-margin trick disappears, and a cell wraps onto the next line as a unit on a phone.

The deciding test

Switch fields off, the way a real shop does

Every pos.entry.* setting currently defaults to on, so a corner shop has to turn most of this off. That is not an edge case — it is the normal state of nearly every tenant. Both mocks below respond to the same switches.

The column order, which matters more than the mechanism

A till is read by position. Whichever option you pick, this is the part your customers will feel — and it is worth getting agreed before any code moves. 

Item  │ Qty │ Price │ Disc │ Type │ Total │ [Add]        ← always
      ├ Batch · Expiry                                     ← pharmacy / veterinary
      ├ Bonus                                              ← distribution
      └ Receivable                                         ← if the shop wants it
  • Stock and Description read better as a hint line under Item than as columns — they are information to glance at, not fields to enter.
  • P/U Price and Profit should leave the counter entirely. They are your cost and your margin, currently on a screen a customer can see over the till.
  • Total and Receivable are derived. They belong in the row as read-only figures, never as inputs an operator can tab into.

What I would do

Option B. A is genuinely cheaper and it would look right on the day it shipped — but it asks the CSS to hold together a structure that is already fighting itself, and it leaves the two-elements-in-step problem exactly where it is. B removes the reason the current layout is fragile rather than restyling around it, and the configuration switches — the feature this screen exists to support — become impossible to get wrong.

Neither touches an id, a name, or DOM order, so Enter-chaining, focus flow and the P7 gates should all stay green. I would re-run P7.1 and P7.2 to prove it rather than assume it.

Worth saying plainly: this changes how the till looks, not how much of it there is. Sixteen fields arranged beautifully is still sixteen fields. The layout is worth fixing — but the complaint that it is “not simple” is mostly answered by the defaults, and every pos.entry.* setting currently ships on.
