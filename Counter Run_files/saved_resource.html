01 — What the registration form does

#ProductDiv opens a full-viewport overlay driven by catalog-products.js, writing to catalog-service through the monolith proxies. Beside the form sits the Already registered panel — the tenant's whole catalogue, deactivated products included, narrowed live by what is typed into Name / SKU / Barcode, with an edit this one link on every row. It exists so a near-miss is corrected instead of duplicated.

02 — Findings

Four of these are reproducible from the script below. Two are notes, so nobody files them twice.

#SeverityFindingCase
F1High Barcode uniqueness is enforced nowhere. The client duplicate check covers SKU only, and ProductService.create/update check only existsBySkuScoped — there is no existsByBarcode in the repository. Two active products can carry the same EAN, after which /products/lookup and /products/scan resolve whichever the query returns first. PR-7
F2Medium A pack size cannot be un-set. fromDto reads packSize == null as "not supplied" — right for CSV and integration callers — and the form posts null for an emptied box. Clearing Holds N pieces hides the loose row for the session but leaves the product divisible in the database, while allowLoose does clear. The product ends up with a pack size and no permission to split it. PR-11
F3Medium The own-stickers panel is nested inside the loose row. #prodStickerWrap sits inside #prodLooseWrap's .col-sm-4 > .row, so loadProductStickers() shows it into a hidden ancestor. On a saved product with packSize ≤ 1 the panel never appears; when it does appear it is squeezed into a one-third-width column. A shop printing PACK stickers for non-divisible goods cannot reach the feature. PR-14
F4Medium A product cannot be renamed. editProduct() ends with updateReadOnly(true), which disables #prodName. Nothing in the product path ever calls updateReadOnly(false) — only the global [id^="reset"] handler does — so Name stays disabled on the next product too. PR-16
F5Low A blank sell price is stored as 0, not null (s2n('') → 0), so an unpriced product reads as free in pickers and reports rather than "no price set". PR-1
F6Note The client SKU check reads a snapshot taken when the form opened, so a colleague registering the same code a minute ago is invisible to it. The server is the real gate — and a failed index load must render the panel's error state, never an empty list that reads as "nothing is registered". PR-5 · PR-8
F7Note Duplicate names are legal by design — same product, different pack or maker. The blur check advises and highlights the namesake row. Do not file it. PR-6

03 — Product registration

Twenty cases. Four are expected to fail on today's build and are marked as such — a pass there is news, not a mistake.

PR-1

Bare minimum: name only

owner.business@ · Registration → Product → New Product

  1. Type a name only (Manual Test Widget). Leave SKU, barcode, price, tax, unit, category and manufacturer blank.
  2. Submit.
Expect

Saves. The row appears in the grid with an empty SKU, and the product is offered in the purchase and sell pickers.

Watch — F5

The price column shows 0.00, not blank. Note whether that is acceptable for the shop.

PR-2

Name is mandatory on both sides

  1. New Product → leave Name empty → Submit.
  2. Enter only spaces → Submit.
  3. By API: POST /addProduct with {"name":""}.
Expect

Steps 1 and 2 give an inline error with no request sent. Step 3 is refused by @NotBlank: "Product name is required". A nameless product cannot be created by either route.

PR-3

Two products with no SKU

  1. Register Widget A with no SKU.
  2. Register Widget B with no SKU.
Expect

Both save.

Watch

"Product SKU already exists: " is the old blank-collides-with-blank bug — a blank is reaching the column as '' instead of NULL.

PR-4

Duplicate SKU is refused

  1. Register Widget A with SKU MT-100.
  2. New Product → SKU MT-100 → tab out of the field.
  3. Correct it to MT-101 and save.
  4. Repeat step 2 with mt-100 — different case.
Expect

Step 2 turns the box red immediately with the reason and blocks Submit; step 3 saves; step 4 is also blocked, because the client compares lower-cased.

Watch

What the server does with mt-100 if the client check is bypassed — the query is an exact match, so case-folding depends on the column collation. Record the answer.

PR-5

A duplicate created in another session

Two browsers, both owner.business@ — the stale-index case

  1. Browser A: open New Product (the index snapshot is taken now) and leave it open.
  2. Browser B: register SKU-DUP.
  3. Browser A: enter the same SKU-DUP and Submit.
Expect

The client lets it through — its snapshot predates B — and the server refuses with "Product SKU already exists: SKU-DUP" surfaced in the form. Nothing is created.

PR-6

A duplicate name advises, and offers the fix

  1. Register Panadol 500mg.
  2. New Product → type panadol 500mg → tab out.
  3. Now type into SKU, then into Barcode.
  4. Click edit this one on the highlighted row.
Expect

Step 2 warns and highlights the existing row without blocking the save (F7). Step 3 repaints the panel and the highlight survives. Step 4 loads that product into the form and clears the warning — no twin is created.

PR-7

Duplicate barcode

Expected fail · F1
  1. Register Widget A with barcode 8901234567890.
  2. Register Widget B with the same barcode. Record whether it saves.
  3. Sell → type 8901234567890 into #sellScan → Enter.
Today

Step 2 saves, because no check exists. Step 3 resolves to one of the two, arbitrarily.

Wanted

A refusal at step 2, mirroring the SKU rule. File against F1.

PR-8

The panel must never lie about an empty catalogue

  1. Stop catalog-service, or block /getUserProduct in devtools.
  2. Open New Product.
Expect

The red could not load the registered products message.

Fail if

It shows "no products registered yet", or an empty list — a false all-clear given directly before the operator registers a duplicate.

PR-9

Inline category and manufacturer

  1. Type a new category name → +.
  2. Type a new manufacturer name → +.
  3. Save, then reopen New Product.
Expect

Both are added, selected, and the visible button text updates. The category persists as a real entity; the manufacturer appears in the dropdown only after the product carrying it was saved (F7 — there is no master table).

Watch

A button still reading "— none —" while the hidden <select> holds the value: the bootstrap-select refresh regression.

PR-10

Editing must not rewrite the manufacturer

Setup: a product whose brand is on no other product

  1. Open it for edit.
  2. Change only the description, and save.
  3. Reopen it.
Expect

The manufacturer is unchanged.

Fail if

It has become the alphabetically-first brand — a .val() on a missing option falling back to option 0.

PR-11

Pack rules, and un-setting them

  1. New product, unit strip, Holds 10 — the loose row appears. Fill tablet / tablets, tick may be sold by the piece, set sales start as pieces. Save.

04 — Purchase, goods in

Where stock, cost and the vendor's balance all move at once. Every figure here is read again by COGS, the margin guard and the statement.

PU-1

First receipt: stock in, rates stamped

Setup: the PR-1 widget, on hand 0

  1. New Purchase → invoice PINV-001, the widget, QTY 10, P/U 80, S/U 120, date today → Save & Close.
  2. Read the product row: on hand, last purchase, last sale, price.
  3. Record a second purchase with P/U 85 and the S/U box left blank.
Expect

At step 2: on hand 10, last purchase 80, last sale 120, and the catalog sell price becomes 120 — re-price on receive. At step 3 last purchase becomes 85 while last sale and the selling price are unchanged: a cost-only receipt must never re-price what the shop charges.

PU-2

Batch and expiry

owner.pharma@ · needs batchTracking

  1. Receive product X: batch B-1, expiry next month, qty 10.
  2. Receive X again: batch B-2, expiry next year, qty 10.
  3. Go to Sell and pick X.
Expect

The banner names B-1 — earliest expiry, FEFO — not the newest receipt. On hand is 20.

PU-3

Buying by the box

  1. New purchase, product X, toggle Box, packs per box 10, QTY 2, P/U 1000.
  2. Read the hint line before saving.
Expect

The hint states what will actually be stored: 20 packs at 100 each. On hand rises by 20 and the last purchase rate is 100, not 1000. Nothing downstream mentions "box".

PU-4

Box with no packs-per-box

  1. Repeat PU-3 but leave packs per box empty, then save.
Expect

A refusal, or an explicit prompt.

Fail if

06 — The golden thread

One product, registration to statement, run in a single sitting. It doubles as the recording script.

  1. Register Golden Widget — SKU GW-1, barcode 8909998887776, unit pack, Holds 10, loose unit piece / pieces, may be sold by the piece, tax code GST 17%.
  2. Purchase 10 packs at 80, S/U 120, batch GW-B1, expiry next year, vendor on credit, paid 400.
  3. Product list reads: on hand 10, last purchase 80, last sale 120, price 120.
  4. Sell 2 packs and 5 pieces to a walk-in customer.
  5. On hand is now 10 − 2 − 0.5 = 7.5.
  6. The invoice shows 2 × 120 plus 5 × 12, tax at 17%, and batch GW-B1 on both lines.
  7. Sale detail report lists the invoice with the right customer, tax and margin — 120 − 80 per pack, 12 − 8 per piece.
  8. Vendor statement shows 600 outstanding from step 2.

Any figure that disagrees at step 5, 6 or 7 is a stop-and-report, not a retry. Capture the request, the response envelope and the on-hand reading before touching anything else.

Expected failures on today's build are PR-7, PR-11 step 4, PR-14 step 2 and PR-16. Anything else that fails is new.
