This is a live bug in your till today

pos-keyboard.js matches shortcuts on event.key, which is the character the layout produces. On an Arabic or Urdu keyboard the physical S key sends س, so Alt+S — Complete Sale — matches nothing and silently does nothing. Same for park, resume, exact cash and clear cart. event.code says KeyS on every layout on earth.

This platform ships in six languages including ar/ur. Whether it matters depends on something only you know: does any tenant type on a non-Latin layout, or only read a translated screen?

The three mechanisms

Option A · recommended

F7, with Alt+L as an alias

A function key toggles the unit on the current line. Alt+L does the same for tills whose F-row is missing or captured by the OS.

  • Matches the app's existing table — F2 complete, F3 park, F4 resume, F8 exact cash, F9 clear
  • Layout independent: no letter, and the alias reads the physical key
  • No character can reach the quantity box, so the seven numeric readers stay untouched
  • Needs an F-row, or the alias, on the actual till hardware

Safest. It is the only option that adds no new idiom to a keyboard file that has broken twice.

Option B · your suggestion

Shift+L inside the quantity box

The cashier stays in the box: type 5, then Shift+L. Intercepted on keydown, so no character lands.

  • Fewest hand movements — the hand never leaves the number pad area
  • Reads naturally: "five, loose"
  • The only letter shortcut in an app that otherwise uses F-keys
  • Must be matched on event.code or it dies on ar/ur layouts
  • If the interception ever regresses, "5L" parses as NaN and the line silently becomes 1 pack

Fastest. Real risk is the failure mode: it is silent and it overcharges.

Option C · smallest

Touch toggle only

Ship the segmented control and the hint line. No keyboard shortcut at all in this slice.

  • Nothing to learn, nothing to document, nothing to collide
  • Zero changes to pos-keyboard.js
  • A keyboard shortcut can still be added later without redesign
  • A busy counter — the case this feature exists for — reaches for the mouse

Least risk, least benefit. Sound if your tills are touch-first.

All three ship the touch toggle and the hint line. They differ only in whether a keyboard path exists beside them, and which key it uses.

The scanner is the same in all three

The scan box already parses a multiplier. It gains one optional suffix — no new grammar to learn.

CODE1 pack — unchanged
12*CODE12 packs — unchanged
5L*CODE5 loose pieces — new

A scanned manufacturer barcode always means the pack

A GTIN is printed on the pack by whoever made it and cannot mean "one tablet". Treating a scan as loose because the shop happens to sell loose would mis-price the commonest transaction there is. Shop-printed stickers that mean "one tablet" are a later slice.

What I need from you

  1. Which mechanism — A, B or C. If your tills are touch-first or the keyboards have no usable F-row, that decides it.
  2. Does any tenant type on a non-Latin keyboard layout, or is it only the interface that is translated? If nobody does, the Alt-shortcut bug is worth logging rather than fixing mid-slice.

Everything else in U3 is settled and does not depend on this: the toggle, the hint line, the scanner suffix, and the rule that the browser never computes a price — it multiplies a rate the server derived, so the shop can never quote one figure and charge another.
