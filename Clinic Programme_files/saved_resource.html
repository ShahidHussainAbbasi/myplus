Extending the pharmacy into a clinic

Reception takes the patient in, the queue forms, the doctor consults and prescribes, and the medicine is waiting at the counter before the patient walks over. Here is what the platform already does, what is genuinely missing, and the order to build it in so that every phase ships something a clinic can run on.

The verdict

This is an extension, not a new product. A clinic-shaped scheduling service, a prescription and dispensing chain, a drug-safety engine, a shared party master that already knows the word PATIENT, per-tenant capabilities, audit, notifications and money are all built and in front of users. The new work is the clinical record and the consultation itself — encounter, vitals, diagnosis, allergies, orders, results — plus a workspace to run it from.

Three things need settling before any code, because they change the shape of the build rather than its size.

1. The clinical domain must not go into appointment-service

That service was just generalised out of being a clinic — slice SCHED-1 turned Hospital/Doctor/Patient into Venue/Provider/Attendee so a school could book a parents' evening without becoming a hospital, and education now depends on it. Putting encounters and diagnoses back in re-creates the exact defect that slice paid to remove. A new clinical-service on :8097 owns the record; the scheduling core keeps owning time.

2. The AI recommendation is a regulated feature, not a convenience

Software that recommends a specific treatment is, in the EU, a Class IIa medical device under MDR Rule 11; in the US it escapes device regulation under the Cures Act CDS carve-out only if the clinician can independently review the basis of the recommendation. The difference between a shippable feature and a certification programme is entirely in the design — the four rules are below.

3. Staff names are not a design input

"Mr Irshad at reception" is a user holding the RECEPTIONIST role; "Dr Shahid Iqbal" is a user holding DOCTOR plus a provider record. The platform already forbids if (organizationId == 24) by name in its own capability design; the same rule applies to people. Everything below is built for any clinic, then configured for this one.

Standards that change the design

Coded fields carry their code system — decided now, or migrated later

ICD-10 for diagnoses (ICD-11 ready), LOINC for lab tests, ATC plus the national registration number for drugs, SNOMED for findings and allergy substances, CPT or the local schedule for procedures. Every coded field stores (code_system, code, display_text), never a bare string — a code without its system is unusable the first time a second system appears.

Design to FHIR R4 now, expose it later

Do not build FHIR internally. Do map every clinical table to its resource from day one — Patient, Encounter, Condition, AllergyIntolerance, Observation, MedicationRequest, MedicationDispense, ServiceRequest, DiagnosticReport, DocumentReference — so a façade is later a translation, not a rewrite. HL7 v2 ORM/ORU remains the real interface to a lab analyser, and that is a Phase 5 option.

Patient data raises the cost of every shortcut

  • Every read is audited, not only writes — who, what, when, why.
  • Minimum necessary: reception sees demographics and the queue, never clinical notes. A named break-glass path exists, is loud, and is reviewed.
  • The record is append-only. A note is never edited in place — an amendment is a new version with author, timestamp and reason. Same for a signed prescription.
  • Retention class on the row from day one (typically 7–10 years; to age 25 for minors). The purge job is later; the column cannot be.
  • Two identifiers before any clinical act — the doctor's "call next" screen shows name, MRN and date of birth. A queue token alone is never sufficient.

The AI recommendation — four rules, and they are build constraints

Rule 01

Advisory and inert

A suggestion is never a prescription. Nothing is written until the doctor accepts each line, and nothing is pre-ticked.

Rule 02

Show the basis

Every line displays why — indication, class, dose rationale, the patient factors considered. A recommendation the doctor cannot interrogate is what makes this a device.

Rule 03

The model never has the last word on safety

After the doctor builds the final list, from any source, the deterministic engine runs: allergy, interaction, duplicate therapy, rx-required, controlled. Skipping it would be the most dangerous thing in this build.

Rule 04

Constrained to the tenant's formulary

The model may only return product ids from this shop's own catalog, and every id is re-checked server-side. An invented product yields nothing, not a plausible line.

Plus: de-identify before the call — age band, sex, weight, renal and hepatic flags, allergies, current medicines, symptoms, working diagnosis; never name, MRN, phone or address. Log the request and response against the encounter for medico-legal traceability, and record what was suggested versus what was prescribed — the only honest measure of whether the feature earns its cost.

All model calls live in a single assistant-service, which a prior design doc already proposed for the command palette: one place for the credential, the rate limit, the redaction, the cost and the audit. The clinic never holds an API key, and if the model is slow or down the consultation screen still works — templates and manual entry are unaffected.

The programme

Every phase is a complete cycle a real user can run end to end, ships with a passing headed Cypress gate, and leaves the system releasable. No phase needs a later one to be useful.

Reception → queue → consultation → closed visit

The spine. After this, the clinic genuinely runs — on paper prescriptions.

The cycleReception registers a patient, or finds an existing one by phone, takes the consultation fee, and the patient joins the doctor's queue with a token. The doctor opens the queue, calls the next token, verifies name + MRN + date of birth, records the complaint and a note, and closes the visit. It appears in that patient's history. Reception watches the queue advance.

Build
  • clinical-service on :8097, bootstrapped to the platform standard — Flyway, org scoping, method authz, settings, audit, tracing.
  • Tables: patient (MRN, dob, sex, blood group, next of kin, consent, retention class), encounter, versioned clinical note, department.
  • The queue becomes real: queue number, a status state machine (WAITING → CALLED → IN_CONSULT → COMPLETED / NO_SHOW), and real timestamps.
  • Roles: receptionist, doctor, nurse, clinic admin. A CLINIC shape and its capabilities.
  • The consultation fee goes through the existing invoice path — no new money code.
  • A new clinicDashboard: a fast reception intake and queue board, and the doctor's own queue and consultation screen.
  • Closes G-1, G-2, G-3, G-5 and G-7.

Gate  Queue spec run as the clinic's own tenant and across the receptionist / doctor / admin ladder, plus a cross-tenant case. Reception must be unable to open a clinical note; the doctor unable to change the fee.

Prescription → print → the connected pharmacy dispenses

The headline: the medicine is waiting before the patient walks over.

The cycleThe doctor picks medicines from the pharmacy's own catalog, sets dose, frequency, duration and quantity, signs, and prints or downloads a PDF. The prescription lands in the pharmacy queue electronically. The patient walks to the counter, the pharmacist opens the waiting Rx and dispenses through the existing sale — batch, FEFO, expiry, stock and invoice unchanged.

Build
  • The prescription gains an encounter, a prescriber and a registration number, a signature timestamp and a version.
  • Immutable once signed — an amendment is version n+1 with a reason, and the pharmacy is told.
  • The PDF carries clinic letterhead, patient identifiers, prescriber and registration number, every item's dose and duration, a signature block, and a QR code that resolves to the Rx.
  • A "prescriptions waiting" queue on the trade dashboard, one click to dispense.
  • Safety runs at signing; a contraindication is a hard stop with a recorded override reason.
  • Closes G-6 — the controlled register finally records prescriber, Rx id and batch.

Gate  Sign → appears in the pharmacy queue → dispense → stock falls and an invoice is raised. An unsigned Rx is not dispensable; a signed one cannot be edited; a contraindicated pair is refused — asserted on the response envelope, since refusals arrive as HTTP 200.

The clinical record — vitals, allergies, conditions, history, follow-up

Makes the second visit better than the first, which is the whole argument for a record.

The cycleThe nurse records vitals at intake, range-checked, with BMI computed. The doctor sees the patient's timeline — previous visits, diagnoses, medicines, allergies, chronic conditions, risk factors — before saying a word, records a coded ICD-10 diagnosis, and books a follow-up that sends the patient a reminder.

Build
  • Vitals, allergy (substance, reaction, severity, criticality — shown everywhere, permanently), chronic condition, risk factor, coded diagnosis.
  • The timeline is one call and one screen — no request per row.
  • Follow-up reuses the scheduling core and the notification service.
  • Allergy feeds the Phase 2 safety check; a hard allergy is a hard stop.

Gate  An out-of-range vital is refused; an allergy recorded in visit one blocks the contraindicated prescription in visit two; the follow-up reminder is queued.

Prescribing accelerators — templates first, then AI

The client's three sources, built in order of risk: the deterministic ones first.

The cycleThe doctor saves a set he prescribes together as a named template. Next time, the screen offers his matching templates, the patient's current medicines to continue, and — where the capability is on — an AI list with each line's basis shown. He accepts, edits, adds or removes freely. The final list goes through the same safety engine as every other prescription.

Build
  • Templates per doctor, shareable to the clinic, versioned. Ships and gates on their own — deterministic, offline, useful whether or not the AI is ever built.
  • assistant-service: redaction, formulary injection with prompt caching, structured output, server-side formulary validation, per-tenant rate and cost limits, full audit against the encounter.
  • Three clearly labelled sources in one picker, nothing pre-selected, a one-tap "why this?" on every AI line.
  • The capability is off by default, owner-enabled, with the disclaimer recorded per tenant.

Gate  A template loads and is editable. With the capability off the panel is hidden and the endpoint refuses. A fabricated product id in a stubbed response is dropped, not rendered. An unreachable model leaves the screen fully usable. No patient identifier appears in the outbound payload — asserted against the recorded request.

Orders and results — lab, X-ray and imaging, procedures

The cycleThe doctor orders from the consultation screen. The order prints with the patient's identifiers and a barcode. The lab or radiology desk works a worklist, marks the sample collected, enters the result or attaches the report, and it lands back on the encounter — flagged when out of range, with the doctor notified.

Build
  • Order and order items (LOINC / CPT coded, priority, clinical indication), result with unit, reference range, abnormal flag and a named verifier, specimen tracking.
  • Panels — an "LFT" that expands into its constituent tests.
  • Optional HL7 v2 interface to an analyser; for imaging, store the accession number and a pointer — never the pixels.

Gate  Order → worklist → result → back on the encounter with an abnormal flag and a notification. An unverified result is visibly marked as such.

The specialty tail — blood bank, referral, records, oncology

Each a self-contained cycle. Build only what is actually asked for, in the order asked.

  • Blood bank: request → crossmatch → issue → transfusion outcome, with mandatory two-person verification before issue and full traceability from unit to patient.
  • Referral: outbound with a clinical summary, inbound, status tracked.
  • Medical records: typed, versioned, access-audited, virus-scanned documents that are never served from a guessable URL.
  • Oncology — be honest about this one. Protocol regimens, cycle scheduling, BSA-based dosing and cumulative-dose tracking are a specialist product, not a screen. Build the record-keeping subset first, and only when there is a real oncology user.

Gate  One spec per sub-domain, each proving its full cycle.

Money, panels and statutory reporting

The cycleConsultation fees, procedure and lab charges and the pharmacy sale all reconcile. Panel patients are billed to the panel with a co-pay at the counter. Day-end closes. The registers a regulator can ask for print.

Build
  • Charge master, encounter charge capture, panel master and claim, co-pay split, day-end reconciliation.
  • Statutory outputs: controlled-drugs register, notifiable-disease report, patient-data access report, prescriber activity.
  • Ledger posting through the outbox — minding the standing trap that a new posting field must be added in five places or it vanishes silently. Gate the trial balance.

Gate  The day-end equals the sum of the encounters plus the pharmacy invoices, with a panel patient in the set.

Demand-led — FHIR façade, patient portal, teleconsult, inpatient

Admission, beds and inpatient care are a second product, not a phase of this one. An outpatient clinic and an inpatient hospital differ far more than the words suggest, and promising inpatient inside this programme is how these builds fail. Say it early, in writing.

Rules every phase obeys

  1. Tenant isolation on every clinical table — scoped reads, stamped writes, no reachable-by-id holes.
  2. Every read of patient data is audited, not only writes.
  3. Coded fields store the system, the code and the display text.
  4. Clinical data is append-only. Amend, never overwrite; every row carries an author and a timestamp.
  5. The deterministic safety engine runs last, on the final list, whatever produced it.
  6. Capability and shape gating, enforced on the server independently of the screen.
  7. Document numbers from the per-org sequence, allocated late.
  8. Every slice ships a passing headed test, run as the clinic's own tenant, across the privilege ladder, with a cross-tenant negative case.
  9. Flyway per service, deploy-reproducible, no manual step.
  10. No client name and no organisation id in any branch.

Recommended: build and ship Phases 1 and 2, then stop and look. Together they are the entire requirement as it was described — reception, queue, consultation, prescription, pharmacy. Everything after that is depth, and it is better chosen from real use in a real clinic than from a document written before the first patient walks in.
