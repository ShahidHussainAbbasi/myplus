## 1. What "100% end to end" means here, and what it does not

* **Every one of the 87 requirements** in the source design
  ([analysis §1](marketplace-multiseller-analysis.md#1-requirement-register-every-requirement-in-the-source-numbered))
  has at least one test: a unit case, a Cypress gate case or a manual case. That is counted by the script, not
  asserted in prose.
* **It does not mean 87 requirements are built or verified.** The columns say *which kind* of test exists:
  * **Unit:** written **and executed** (`mvn -pl marketplace-service test`, MKT-1a: 60/60).
  * **Cypress:** written **ahead of the code** (the standards' "gate before implementation"). Each spec is
    phase-gated and reports **pending** until its slice is built and the spec is switched on. A Cypress id here is a
    requirement on the implementation, not evidence that it works.
  * **Manual:** written as the walk a person will do. Cases for unbuilt slices are marked *awaiting build* on the
    manual-testing page.
* Requirements for Phases 3–6 are covered by manual acceptance walks only. Their Cypress gates are written when those
  slices are designed, because the screens they would drive do not have a design yet.

### Running the gate

```bash
# switch on the slices that are built; the rest report as pending
npx cypress run --headed --env mkt=1b,1c --spec 'cypress/e2e/marketplace/**'
npm run test:e2e:marketplace          # = --env mkt=all, for the full programme once Phase 1 is built
```

### The contract the specs impose (from `mkt-helpers.js`)

The specs fix the monolith routes (`/mkt/*` for sellers, `/platform/mkt/*` for the operator,
`/marketplace/public/*` anonymous, `/marketplace/*` for the platform customer) and the screen selectors (design
§6.5). Two **test-fixture hooks** are required, seeded behind `app.seed-test-fixtures` **and** the `isProd()` hard
block, like every other fixture:

| Hook | Why the gate cannot do without it |
|---|---|
| `POST /test/mkt/expireNow {sellerOrderId}` | the acceptance window is 5 minutes. The gate must prove a late accept is refused without sleeping |
| `POST /test/mkt/deliverAndSettleOne {sellerEmail}` | drives one order through delivery and the return window so the trial-balance case has a settled commission |

GL account **4500 Marketplace commission** is assumed by MKT-1g-06 (to be confirmed by ruling R-MKT-9).

## 4. Regression each gate guards

| Gate | The regression it exists to catch |
|---|---|
| MKT-0a | a new module visible to every tenant on deploy (live-modules rule). An owner self-granting a module the operator never entitled |
| MKT-1b | two different products merged by name (64GB↔128GB); a client-forged identity key; one seller deciding another's proposal |
| MKT-1c | org ids taken from JSON; regulated goods listed in Phase 1; cost/margin leaking into the public projection; a suspended seller still selling |
| MKT-1d | the cheapest offer forced; a sort that bypasses approval; a page and an API that disagree about an empty city |
| MKT-1e | an order shown as confirmed before the seller accepted (§0b); two sellers in one Phase 1 checkout; a client price honoured; a double submit creating two orders; a hold that never returns |
| MKT-1f | the customer sent to the seller for support; return cost charged to "the seller" by default |
| MKT-1g | money payable before delivery; a ledger line edited in place; a payout approved by its requester or paid twice; commission missing from the books |
| MKT-2 | multi-seller implemented as a front-end filter; a silent variant substitution; a checkout that hangs on one slow seller |
