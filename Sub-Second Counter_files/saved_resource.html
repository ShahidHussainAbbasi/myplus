Sub-Second Counter
R & D proposal · caching, async and the sale path

Getting the counter under one second — at 1,000 tenants

Measured first, then proposed. The headline finding is that the current latency is not bandwidth and not database volume — it is the number of network hops per read, and the fact that the hottest read on the sale path has no cache anywhere.

The diagnosis, in one line

900 ms to move 8 KB is not a data problem. Every read crosses browser → monolith → gateway → service → MySQL, and each hop re-serialises JSON. The payload is irrelevant; the hops are the cost. Caching a payload that is already only 8 KB saves nothing. Removing a hop saves everything.

The hole

The hottest read on the sale path — the product picker — goes to MySQL on every single screen open, and again on every line edit. There is no cache in front of it at any level. At 10,000 products per tenant this does not degrade gracefully; it stops working.

3 · The scale you named, as arithmetic

1,000 tenants × 10,000 records. Two numbers decide the design:

  • 10 million product rows in total, but a counter touches perhaps 200 a day. Retail access is heavily skewed — the same fast-movers, all day. That single fact is what makes caching work here, and it determines which caching.
  • Shipping a 10,000-row catalogue to a browser is indefensible at any cache level. The current picker asks for size=2000, which is already both too large to be fast and too small to be correct.

4 · Proposal — four tiers, in value order

T1

Stop the sale screen paying for the dashboard

Opening the till fires getDashboardChartData and getBusinessDashboardStats — ~1.6 s of work for charts and tiles a cashier is not looking at. Load them when the Dashboard section is actually shown. No new technology, no new failure mode, and it is the single biggest win available.

T2

Two-level cache on the hot reads: Caffeine (L1) + Redis (L2)

Products, customers and stock levels, keyed tenant:entity:id. L1 Caffeine in-process answers in microseconds and removes the hops entirely; L2 Redis — already running — means a restarted or scaled-out instance warms instantly instead of stampeding MySQL. Spring's CacheManager supports exactly this composition, so it is configuration rather than a new framework.

T3

Replace the catalogue dump with a server-side typeahead

The picker should ask for what the cashier typed, not for everything. A prefix search over an indexed column, capped at ~20 rows, cached per tenant. This is the only tier that must happen before 10,000 records — the others make things faster, this one keeps them possible.

T4

Push non-essential work off the sale, using the outbox that already exists

A sale must persist the invoice, move stock and take the money. It does not need to wait for GL posting, audit trails, notifications or analytics — and the transactional outbox already carries several of those. Extend the pattern; do not introduce a message broker to do what it already does.

5 · What I would not do

Not this

Redis as the primary cache for everything. A Redis GET is a network round trip — about 1 ms locally, more across a network. That is a thousand times slower than an in-process hit, and it would put a new hop on the path whose hops are already the problem. Redis belongs behind Caffeine as the shared warm tier, not in front of it.

Nor this

A message queue for reads. Kafka, RabbitMQ and friends make writes durable and decouple producers from consumers. They do not make a read faster, and adding one here would buy operational weight against a latency problem it cannot address. Async is the right answer for T4's writes and the wrong answer for T1–T3's reads.

And a caution on cache keys

Every key must carry the tenant. A shared cache without org_id in the key is a cross-tenant data leak with good performance — the worst possible outcome, because it looks like success. The existing TenantCache already enforces this shape and should be the only way a cache is created.

I measured the read path, not the write path. Before committing to a sub-second confirm, the next step is to measure what addSell does synchronously — inventory reserve and confirm, credit checks, document numbering, serial claims — and which of those genuinely must block the receipt. Proposing a fix for an unmeasured number is how a performance project spends effort in the wrong place.

7 · Suggested order

Each is independently shippable and independently gated, per the standing cadence:

  • T1 first — largest measured win, no new technology, essentially no risk.
  • T3 second — the only item that is a correctness requirement at 10,000 records, not just a speed one.
  • T2 third — real work, and worth doing once T1/T3 have removed the calls that should not exist at all. Caching a call you deleted is wasted effort.
  • T4 last — after the write path is measured, so the decision rests on numbers rather than on the assumption that it is slow.
