MaxTheService Performance Review

Engineering review · MaxTheService

Why it is slow, measured — and what actually fixes it

A end-to-end performance and reliability review, prompted by a reported delay when adding stock on the product form. The button was not the problem. Four defects were, and three of them are the same defect.

Measured 9 September 2026 against the running stack · org 13 · 1,000 products · 807 sale lines · 4,510 stock rows

The architecture is not the problem. Every issue found is work the system should not be doing at all — a list with no ceiling, a query repeated per row, a round trip that asks for an answer it was already given. Adding servers would have carried the cost, not removed it.

The measurement that changed the plan

The obvious fix for a 1.76 MB reload is to load fewer rows. Measured, it does almost nothing: q=5 returns 11 KB and still costs 1.19 s. The server loads every row from the database and truncates the list in Java. The queries are the cost, not the bytes — so capping the payload would have cost the grid's client-side search and bought back nothing.

02The four causes

C‑1 · Pagination has never run proven

business-service has had paged reads since slice 24. The monolith proxy forwards one parameter and drops page and size on the floor: 

String q = request.getParameter("q");
return client.get("/getUserSell", q != null ? "q=" + q : "");   // page/size dropped

Requesting size=25, 50, 100, 200, 400 returns exactly 1,758,072 bytes every time. The paged branch is unreachable.

This is the fifth instance of one pattern in this codebase — the GL outbox dropping event fields, the product projection, the monolith SellDTO, addProductStock dropping cost, now this. The shape to distrust is a hand-built parameter list over a call that already has the parameters. 18 proxies build their query by hand; 12 pass it through.

C‑2 · N+1: 1,615 queries for one screen fixed

Sell.customerHistory is @OneToOne(EAGER) and CustomerHistory.customer is @ManyToOne(EAGER), with no join fetch and no @EntityGraph. EAGER does not mean joined — it means fetched before the entity is returned, one query per row: 

    1  select the 807 Sells
  807  select each Sell's CustomerHistory
  807  select each CustomerHistory's Customer
─────
1,615 round trips to MySQL for ONE screen

At 10,000 sale lines that is 20,001 queries.

C‑3 · No batch fetching fixed

default_batch_fetch_size was unset platform-wide. One line in the shared config collapses C‑2's follow-up queries from 1,614 to about 17, for every service, with no code change.

C‑4 · The mapper was reconfigured once per row fixed

modelMapper.addConverter(...) sat inside the per-row loop — 1,614 calls for one response, each dropping the mapper's internal type cache so the next row rebuilt it. Found in three places, not one: Sell, Customer and Purchase.

03Two more that cost every call

No connection pooling between the monolith and the services fixed

new RestTemplate() uses HttpURLConnection: a new TCP connection for every proxied call, and no timeouts at all. Every screen makes 5–15 proxied calls. The class's own log line already recorded the consequence — "the RestTemplate below has NO timeouts, so this is the shape a hung downstream takes."

Now a pooled java.net.http.HttpClient behind JdkClientHttpRequestFactory, with a 5 s connect and 30 s read timeout — and no new dependency.

Stock rows grow forever open

Every stock add appends a stock_entries row and never merges. 4,510 rows for 3,624 products; the worst product carries 80; 206 are exhausted but still read on every refresh.

03bA functional bug the profiling uncovered

Not a performance issue — a correctness one, found by reading the container log while measuring something else. It affects exactly the population that reported slowness.

Product names are blank on the Sale grid — silently

/getUserSell resolves display names by asking catalog for every distinct product on the result in one GET. Org 13 has 730 distinct products on its sale rows. Catalog answers with a bare Tomcat HTTP Status 400 – Bad Request — the request line plus the bearer JWT exceeds the 8 KB header limit.

It fails on every single call. The catch turns it into a WARNING and an empty map, so the grid renders with no product name, SKU or description on any row and nothing on screen to explain why.

It gets worse with tenant size. The more products a shop has sold, the longer the URL, the more certain the failure — which is why it shows up for large customers and never in testing.

Fixed by chunking the lookup at 100 ids — 8 calls instead of one oversized one, and a partial failure now degrades partially instead of blanking every row. Applied to the Sale and Purchase grids. Three further callers share the shape and should be reviewed: SerialUnitController, SellService, and pharma's SafetyService.

And the microservices are running without the prod profile

SPRING_PROFILES_ACTIVE is set on the monolith and on none of the microservices. They therefore run the default config, where org.hibernate.SQL is DEBUG and org.hibernate.orm.jdbc.bind is TRACE — every statement and every bound parameter written to the log.

application-prod.yml sets both to WARN. It is simply never activated. On a request that runs 1,615 queries, that is thousands of formatted log lines — and bound parameters mean customer data is being written to container logs.

The single number that disproves tenant isolation

8. That is DB_POOL_MAX — the requests per service that can touch the database at once, against 200 Tomcat threads. The other 192 queue.

Before today's fix, /getUserSell held a connection for 1.2 s. Eight concurrent report loads from one tenant would have blocked every other tenant on that service — no error, no log line, just everyone waiting. Scoping is not isolation; capacity is.

The single fact that blocks horizontal scaling

There is no spring-session, and TokenStore is @Scope(SCOPE_SESSION) — it holds the JWT every downstream call needs. A second monolith instance would log users out on alternate requests without sticky sessions, and one restart drops every user's token. The platform is vertically scalable only.

Correcting an earlier assumption of my own

I expected the 1.76 MB payload to dominate for remote clients. It does not — gzip is enabled and working: 1,758,072 → 85,543 bytes. Transfer is not the problem.

That makes the 95 requests on HTTP/1.1 the dominant remote cost. Browsers open about 6 connections per origin, so 95 requests is roughly 16 sequential round trips before the page settles. On a 200 ms link that is over three seconds of pure latency, spent entirely on waiting.

07The roadmap, with two changes

Your 30/90/later sequence is right. Two items are in the wrong order, and one is missing.

Move to first: observability

Your list has SLOs on day one and dashboards at 90 days. They are the same task and the dashboard has to come first — /actuator/prometheus is listed in the config and 404s at runtime, because micrometer-registry-prometheus is on none of the 22 services. An SLO set before the histogram exists is a guess; set above today's p99 it promises nothing, set below it is breached on day one. Instrument, baseline a week, then commit to numbers.

Move earlier: request count

"Reduce dashboard initial request count" sits mid-list. Given gzip is already working, it is the largest remaining win for remote clients — 95 requests on HTTP/1.1. Enabling HTTP/2 at a reverse proxy addresses it without touching the application.

Missing: make the monolith stateless

Nothing in the roadmap addresses in-heap sessions, and every scaling item depends on it. spring-session-data-redis — Redis already runs for the gateway — is the unlock, and it also stops a restart logging every user out.

Agreed without reservation

Terminating TLS at a reverse proxy. Tomcat's 8080 is currently the edge, with no proxy or WAF in the compose stack — that same proxy is where HTTP/2 belongs.

And the Kubernetes judgement: adopt it when orchestration is the constraint, not before. Nothing found here is a scheduling problem.

09What was not checked

  • Browser rendering. Every number here is server-side. A p95 the user feels includes laying out 807 rows in a DataTable, which was not profiled.
  • Production traffic. The proposed SLOs come from local measurements, not from real usage — which does not currently exist in a form anyone can query.
  • The AWS side. Terraform for ECS/Fargate is recorded elsewhere but absent from this tree; autoscaling may already exist where it could not be seen.
  • The other 21 services. Business was traced end to end. The pool, thread and metric findings are platform-wide by construction, but per-service hot paths were not.
