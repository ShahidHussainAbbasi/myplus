Installments Acceptance Walkthrough

Shahzad Mobile Shop · acceptance

Validating the installments build, end to end

Two routes: the automated gates prove the code, and the counter walkthrough proves the shop can actually do the job. Run both — they fail in different ways.

Before anything: is the right build running?

More time has been lost this week to testing a stale build than to any real defect. Two checks, ten seconds. 

docker ps --format "{{.Names}}\t{{.Status}}"     # business-service + monolith healthy?

docker exec myplus-business sh -c 'ls -l /app.jar'   # same size as
ls -l microservices/business-service/target/*.jar     # this one?
Container timestamps are UTC and yours are UTC+5, so a five-hour difference means the same file, not a stale one. Compare the byte size — that is unambiguous.

Route A · the automated gates

Eight specs, roughly six minutes total. These prove the arithmetic, the books and the refusals. 

mvn -pl business-service -am clean install -DskipTests
mvn -pl business-service test          # expect 179 passing, 0 skipped

npx cypress run --spec cypress/e2e/business/installment-plan.cy.js
npx cypress run --spec cypress/e2e/business/installment-screen.cy.js
npx cypress run --spec cypress/e2e/business/installment-aging.cy.js
npx cypress run --spec cypress/e2e/business/installment-statement.cy.js
npx cypress run --spec cypress/e2e/business/installment-worklist.cy.js
npx cypress run --spec cypress/e2e/business/installment-reminders.cy.js
npx cypress run --spec cypress/e2e/business/installment-serial.cy.js
npx cypress run --spec cypress/e2e/business/installment-repossession.cy.js
One spec at a time. Running two at once is what produced the document-number collisions, and it cost three separate misdiagnosed failures. --no-exit keeps the browser alive, so pasted commands overlap.
Expect 179 unit tests with 0 skipped. A skipped count above zero means the container tests are not running and the migrations, invoice money, sale atomicity and tenant scoping are all unproven.

Route B · the counter walkthrough

What the gates cannot tell you: whether a shopkeeper can find it, read it, and act on it. Do this as the owner, on the Business dashboard.

First, switch the feature on

Settings → Configuration, group Installments. Everything is off by default on purpose — a default is not a decision.

SettingSet toWhy
pos.installment.enabledtrueShows the terms panel on the sale screen.
pos.installment.serialRequiredtrueA phone shop should not finance a handset with no IMEI.
pos.installment.remind.enabledtrueBuilds the chase list.
pos.installment.repossession.enabledtrueAllows a defaulted plan to be closed by taking the handset back.
…repossession.minOverdueDays30A customer three days late keeps their phone.
…repossession.protectedGoodsPct66Once two thirds is paid the goods are protected — taking them can void the debt.

  1. Sell a handset on terms

    Sale screen → add a handset → Enter Manually for the customer → payment method CREDIT → tick Sell on installment. Enter 6 payments, a first due date, and the IMEI.

    Expect the schedule to appear before you commit, and the six amounts to add up to the price exactly. This is what gets read aloud to the customer.

  2. Try to finance the same IMEI again

    Ring up a second sale on terms with the same IMEI.

    Expect a refusal that names the plan already holding it, so the cashier knows where to look. The sale must not go through.

  3. Take a part payment

    Customer → Receive Payment. Pay roughly two and a half instalments.

    Expect the first two instalments PAID, the third PARTIAL with the exact residual, and the customer's total outstanding to drop by what was paid — no more, no less.

  4. Read the Installments screen

    Sale → Installment plans. Check the financed, paid and remaining figures, and search for the customer by name.

    Expect the three figures to agree with what you just paid, and a late plan to show a red overdue count while a current one shows none.

  5. Work the chase list

    Same screen → To chase tab. Press Rang on a row and record what the customer said.

    Expect the phone number on the row, and the call to be remembered afterwards — greyed out with the outcome. That memory is the whole point: without it the shop rings the same customer three times and never rings another.

  6. Print the customer's statement

    Customer → Statement.

    Expect the transactions first, then an Upcoming instalments block with each due date and a balance counting down to zero. The closing balance must equal what the customer actually owes — not double it.

  7. Check the aging report

    Receivables aging.

    Expect only the late instalments to age, not the whole plan balance. A customer paying on time must not read as a 90+ delinquent.

  8. Repossess a defaulted handset

    Installment plans → click the plan → choose the condition → Repossess.

    Expect the unpaid balance written off, the plan closed, the customer owing nothing, and no refund of what they already paid. Then re-sell the same IMEI — it should be free again, because closing the plan releases it.
    Also try the refusals: a customer only a few days late, and one who has paid two thirds. Both must be refused with a reason a shopkeeper can act on — the second mentions a court order, and that rule is what keeps the shop out of one.

  9. Check the books

    Finance → Trial balance, after all of the above.

    Expect it to balance, and the customer's closing balance to be zero to the paisa.
    A balanced trial balance is not proof the numbers are right. A posting can be internally consistent and still be for the wrong amount — that is exactly how a customer was once left two paisa in credit. Check what the person owes, not only that the ledger is tidy.

Leave the tenant as you found it

Switches left on change behaviour for every later test and for the live shop. Turn serialRequired, remind.enabled and repossession.enabled back off unless the shop is genuinely going live with them.

This has bitten already. A spec left serialRequired on when its cleanup hook died, and an unrelated test file dropped to 1 of 6 with every sale refused — for a reason nothing in that file could explain.
Route A proves the code is correct. Route B proves the shop can use it. A build that passes only one of them is not finished.
